# Lessons — Outreach & Follow-up

Accumulated lessons for outreach, follow-up, and warm-leads. Add new outreach lessons here as they arise.

## Outreach
- **SMS is the fallback for businesses without email.** If a business has a mobile number but no email, send outreach via SMS using `python3 scripts/imessage.py send` (or `python3 scripts/twilio_sms.py send` if you configured Twilio). Only mark as `unreachable` if the number is a landline AND no email/social media exists.
- **Sound human, not AI.** No em dashes, no filler phrases ("I wanted to reach out"), use contractions, keep it under 150 words.
- **Don't combine compliments that backfire.** "39 reviews after 25 years" implies they should have more. Keep review count and years in business as separate compliments.
- **Be precise about facts.** Review counts, star ratings, years in business - the owner knows these intimately and will notice if wrong.
- **Log ALL outreach to Supabase immediately, including manual sends** (social media DMs, contact forms) — mark those clients `outreach_sent` right away, or other sessions will see them as incomplete and try to re-outreach. Supabase is the single source of truth for pipeline state.
- **Always check Supabase before sending any outreach.** Even if an email bounced, a previous session may have already resent via SMS. Check the client's current outreach status and channel before sending to avoid duplicates: `python3 scripts/db.py client SLUG`.
- **Check your email provider's Sent folder before sending any email.** Before sending a follow-up email, search the Sent folder for emails TO that client sent today. If one already exists, skip it. This prevents duplicate sends when batch scripts overlap or get restarted. Same applies to SMS — check chat.db (iMessage) or Twilio history for outgoing messages today before sending.
- **Always put the mobile number in the `phone` field.** The `phone` field is used for SMS outreach. If only a landline exists, put it in `phone`. If both exist, put mobile in `phone` and landline in `landline`. Never store a landline in `phone` when a mobile is available - it causes SMS sends to fail.

## Outreach Safety
- **Always read `deployed_url` from Supabase, never reconstruct the URL from the slug.** Vercel truncates project names at ~35 characters and Cloudflare Pages appends random characters on a name collision, so a slug-templated URL can 404 while the live site is fine. Copy `deployed_url` verbatim into any message. The send-side `verify_urls_in_message` guard will catch a 404, but that's a safety net — get it right at compose time.
- **Send scripts verify URLs before sending.** The send scripts check that every deployed-site URL (`vercel.app` / `pages.dev` / `netlify.app`) in the message body returns HTTP 200 before sending. If any URL is broken, the send is blocked with a clear error. This prevents sending dead links to clients. If you hit this block, fix the deployment first, then retry.
- **Read the conversation before EVERY send.** Before sending any SMS or email, read the full thread (`imessage.py read` or `twilio_sms.py read` per `SMS_PROVIDER` / `gmail.py search`), then reason about whether the proposed message makes sense in context. Check for: duplicate messages already sent today, recent replies, messages from other sessions, wrong follow-up number, tone mismatches. Never send blindly from a list - even in batch operations, check each thread individually first.
- **Verify threading before sending replies.** After calling `gmail.py reply`, the email can still land as a separate thread if the `References` header is incomplete. Before sending, read the thread with `gmail.py search`, extract the `References` header from the most recent message, and pass it via `--references` with the full chain of Message-IDs appended. If in doubt, manually verify the Message-ID chain makes sense. A reply that breaks the thread looks unprofessional.
- **After stopping a background send script, always check the SMS thread (chat.db or Twilio log) for what actually went out.** Scripts can send messages before being killed. Assuming "stopped = nothing sent" leads to duplicates.
- **`imessage.py read` can silently lose message bodies if the regex is too tight.** On macOS Ventura+, sent iMessages frequently store *only* a control prefix (`tring+` / U+FFFC) in chat.db's legacy `text` column, while the real body lives in the `attributedBody` BLOB. A previous parser used `text or extract_text_from_attributed_body(abody)` — short-circuiting on truthy `text` — and an over-greedy regex `(?:\x00.*)?NSDictionary` that swallowed the message text along with the attribute trailer. Result: real messages rendered as bare `tring+`, which warm-leads then misclassified as tapbacks. Lesson cost: a warm lead was misclassified as needing a nudge after a 19-day gap that was actually 3 days, because the parser produced bare `tring+` instead of the real message body. Fix: anchor on `NSString\x01\x01+` + length byte and terminate on `\x02` + alpha (the real attribute trailer); always prefer `attributedBody` over `text` and only fall back to text if the BLOB yields nothing. If you ever change the parsing again, regression-test against a mix of: short messages (single-byte length), long messages (multi-byte length collapsed to `\x00` after errors=ignore), and tapbacks (no body at all).
- **Threading is a property of the recipient's mailbox, not the headers we send.** When the prospect replies from a *different* address than the one we outreach to (e.g. our chain went to `contact@business.co.uk` but they hit reply from their `business@gmail.com`), perfect `In-Reply-To` + `References` headers still won't thread on their side because their mailbox has never seen the prior Message-IDs. Symptom: our reply lands as a standalone message in the prospect's inbox. Fix: when the reply-from address differs from the original outreach-to address, **Cc the original address** so the chain stays intact at the mailbox where it lives, and the prospect still sees the new message at the address they're actively reading. `gmail.py reply` now does this automatically: it walks the `--references` chain, looks each Message-ID up in your Sent folder, and auto-Cc's any prior recipient address that differs from `--to`. There's also an orphan guard — if no prior thread can be found at all (no match at the recipient's address AND no related mailbox in references), the send aborts unless `--accept-orphan` is passed. Lesson cost: a prospect replied from Gmail to a chain originally sent to their branded mailbox; the reply orphaned because we sent only to Gmail with no CC.
