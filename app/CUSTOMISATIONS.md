2026-08-15 — **Skill resolution fixed: the customised skills were on disk but were not what loaded.**
A real `/build` run rendered the vendor SKILL.md, not ours — the `anti-ai-slop` bullet was simply
absent from the body. Cause, read out of the shipped Claude Code bundle rather than inferred:
Claude Code names a skill by its **directory name** and ignores `name:` frontmatter, so this install
has three skills called `build` (`app/.claude/skills/`, `app/.klaudius/base/.claude/skills/`, and
`../pristine/.claude/skills/`, the last two byte-identical). Static project skill dirs are found by
walking UP from the session's cwd; the repo root has no `.claude/skills`, so when the pipeline is run

sorts deepest-first, and writes them into a map keyed by bare name so the DEEPEST copy is written
last and wins — `.klaudius/base` is deeper than `.claude`. A module-level cache means each directory
registers only once, so whichever tree is touched first owns the name for the rest of the process.

which makes `app/.claude/skills` a STATIC source — and static sources beat dynamic ones by name, so
base and pristine can no longer take it. Backed by `deny` rules on Read/Edit/Write under
`.klaudius/base/**` (here) and `pristine/**` (repo root) so the shadow trees can never register at
all; `grep`/`diff`/`git` through Bash still work on them and do not trigger skill discovery.
Verified by invoking the skills, not by grepping files: from `app/`, `build` loads with the
`anti-ai-slop` bullet and `deploy` loads with `§ IndexNow ping (all hosts)`; from the repo root
`build` resolves to SuperClaude's `~/.claude/commands/build.md` (first line
`# /sc:build - Project Building and Packaging`) — a different product entirely.
Affected all five customised skills — `build`, `outreach`, `deploy`, `seo`, `cms`. Regression guard:

2026-08-15 — **FIXED: webfonts silently dropped from every build. Real mechanism found, generator
fixed, guard added.** Supersedes the same day's earlier webfont lesson entry, whose diagnosis
("a remote `@import` is dropped; version-dependent") was incomplete and led to the wrong fix.

**Mechanism, bisected one URL feature at a time and diffed against the emitted CSS each time:**
Turbopack (the Next 16 default builder) silently drops any remote `@import` whose URL contains a
literal **comma**. Kept: `family=Space+Grotesk`; `family=X:wght@300;400;500` (semicolons); two
`&family=` params; the same URL with the comma written `%2C`. Dropped: `wght@300,400,500`;
`Bodoni+Moda:opsz,wght@6..96,400`; and `https://example.com/a,b/style.css` — a comma in the *path*,
so it is not a query-string or Google-Fonts issue. Position in the file, `output: 'export'`,
`url()` vs bare string, and a `layer()` clause are all irrelevant. It is **Turbopack-specific**:
identical source built with `npx next build --webpack` keeps the `@import` and its fonts. PostCSS
is innocent — running the project's own `postcss` + `tailwindcss` config by hand emits the
`@import` intact, so the loss happens downstream in Turbopack, which drops the whole at-rule and
emits **no warning**. This retires the "version-dependent, a fresh `npm install` picks it up"
guess: `klaudius-cms-smoke` kept its `@import` purely because its URL
(`Figtree:wght@300;400;500;600;700`) has zero commas. Nothing about the version differed.
Every real Google Fonts pairing URL has a comma — an axis tuple or a comma-separated weight list —
and `/ui-ux-pro-max` hands the pairing over as a literal `CSS Import: @import url(...)` line, so
the vendor's own workflow produces the broken form by default.

**Fix (generator, not one client): `next/font/google` in `layout.tsx`.** It self-hosts the woff2
into the build, so there is no remote request to lose, no third-party dependency and no FOUT. The
`--font-display` / `--font-body` custom properties stay in `globals.css` and now point at the
`--font-*-src` variables next/font exposes. Mandated in `.claude/skills/build/SKILL.md` (new
"How to LOAD the fonts" section under § Font, with the exact tsx/css pattern, plus a gate in
§ Verify) and applied to both existing clients. A `<link rel="stylesheet">` also survives the
build, but it keeps the third-party request and cannot be proven locally in a sandbox that blocks
cross-origin font CSS, so next/font is the mandated path.

**Guard: `scripts/font-check.mjs` (new).** `node scripts/font-check.mjs clients/<slug>/site` →
`FONT_CHECK=PASS|FAIL`, non-zero exit on FAIL. Two layers: (1) artefact — counts `@font-face`
rules and self-hosted font files in `out/`(or `.next/`), counts remote font `<link>` tags in the
HTML, and flags any comma-carrying remote `@import` still in `globals.css`; (2) rendered — serves
`out/` on an ephemeral port, loads it in Chromium, waits on `document.fonts.ready`, and for
`body`/`h1`/`h2`/`h3`/`p`/`nav a`/`a`/`button` width-probes the first declared family against
serif, sans-serif and monospace baselines, cross-checked against the families in `document.fonts`.
Degrades to artefact-only with an honest warning on a server app (no `out/`); `--url` targets an
already-running server. Wired into `.claude/agents/qa-reviewer.md` (Step 3 runs it; Step 4 has a
hard-FAIL checklist item quoting it) and `.claude/skills/build/SKILL.md` § Verify.

**Why it is deliberately NOT a computed-style check.** `getComputedStyle(el).fontFamily` returns
the *declared* stack whether or not the face ever loaded — on the broken build the `h1` still
computes to `"Bodoni Moda", Georgia, serif` while rendering in Georgia, so a computed-style
assertion would have passed the very bug it was meant to catch. `document.fonts.check()` false-
greens too: per spec it returns **true** for any family that needs no loading, i.e. true for every
unknown family that silently falls back (it returned true for all eight selectors on the broken
build). The width probe is what actually fires. It also reports the case where a family renders
only because it is installed on the operator's own machine while the page ships no `@font-face`.

**Proof, on `impact-landscapes-frisco`, artefact + rendered + viewed screenshots at 1440x900:**
BEFORE — 0 `@font-face`, 0 self-hosted font files, `document.fonts.size` 0, `h1` 942px wide,
`FONT_CHECK=FAIL` with 10 failures. AFTER — 41 `@font-face`, 7 self-hosted woff2,
`document.fonts.size` 41, the same `h1` 865px wide, `FONT_CHECK=PASS`. The declared computed
`font-family` names "Bodoni Moda" first in **both** states; only the rendered width and the
screenshots separate them (didone hairlines and Space Grotesk body vs Georgia and Helvetica).
`klaudius-cms-smoke` converted too — 20 `@font-face`, 10 self-hosted files, PASS.

2026-08-15 — **notify.sh fork bomb closed with a depth guard that actually counts.** Three defects, of
which only the third was still live when this lane picked it up.

1. The original fan-out re-invoked self as `NOTIFY_CHANNEL="$c" "$0" ...`; the child re-sources `.env`,
   got the comma list back and fanned out again. Fixed earlier by `NOTIFY_FORCE_CHANNEL`, a name `.env`
   never sets.
2. `${NOTIFY_FORCE_CHANNEL:-...}` used `:-`, so an EMPTY forced channel fell back to the comma list.
   Fixed by `${VAR+set}`, which tests presence rather than emptiness, plus an explicit
   `[ -n "$CHANNEL" ] || exit 0`.
3. **The `NOTIFY_DEPTH` backstop added after the second incident was INERT.** It was read, sanitised,
   compared (`-gt 1`) and exported — but never incremented. Every process in a chain therefore exported
   `0`, and `0 -gt 1` is never true, so the guard could not fire at any depth. Proven by tracing
   `NOTIFY_DEPTH` at each level of a real fan-out against a sanitised copy of the live `.env`: parent and
   both children all logged `DEPTH=[0]`. **A guard that cannot fire is worse than no guard, because it
   reads as covered in review** — which is precisely why the second incident was not caught.

The fix is `NOTIFY_DEPTH=$((NOTIFY_DEPTH + 1))` on ENTRY (before any channel logic), exported, refusing
above 2 with a non-zero exit. Sited at entry rather than at the fan-out on purpose: it bounds recursion
arriving through *any* path, including a future cycle that never touches the fan-out at all (the email
branch already shells out to `gmail.py`). Depth 1 = the caller's invocation, 2 = a fan-out child, 3 =
a grandchild this script has no legitimate reason to produce. Total processes are capped at
`1 + number_of_channels` no matter which of the two conditional fixes above is later reintroduced.

`exit 3` is deliberate, and is the one place this script is loud: everywhere else it exits 0 so a missing
channel never fails a pipeline, but a silent 0 here is exactly what let the first bomb reach 3,530
processes unnoticed. Verified safe for every caller — `db.py::_notify` uses `check=False`, the fan-out
uses `|| true`, `outreach-notify-simple.sh` uses `|| exit 0`, and the skills invoke it as a bare command
whose status nothing reads.

⚠️ **The originally-reported "second path in" was never reproduced, and the report of it was wrong on one
point.** With the real `.env` (`NOTIFY_CHANNEL=telegram,slack`, no `NOTIFY_FORCE_CHANNEL`) the fan-out
terminates correctly at exactly 3 processes, depth 2 — confirmed against a credential-stripped copy of the
live file, not a synthetic one. Eliminated by evidence, not by argument: `db.py::_notify` passes an
**absolute** path (so `$0` cannot mis-resolve) and has no retry loop; there is exactly one `"$0"`
self-invocation site in the file; only one `notify.sh` on the whole machine has a fan-out and it carries
the guard (`pristine/` and `.klaudius/base/` have no fan-out at all); no Claude hook references
`notify.sh`; `.env` is byte-clean with no trailing/doubled comma and parses without syntax error. What
made the guard reachable is defect 3 above, which is path-independent — so the depth counter closes the
unreproduced path too, which is the entire reason the fix is a counter and not another conditional.
